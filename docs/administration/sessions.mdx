# Sessions

## Active sessions {/* #active-sessions */}

**You want to:** see who is signed in, or end someone's sessions now.

**Admin → Sessions** lists every sign-in token with the user, its status, address and browser, when it was issued and
last used, and when it expires if nothing more happens. *Only active sessions* hides expired and revoked ones.

<Screenshot id="admin-sessions" alt="Admin → Sessions: active sessions of ayse.yilmaz, bob, alice and admin with address, browser, issued, last used and expiry, and revoke buttons" />

- The **bin** on a row signs out that one session; the other button signs out **every** session of that user.
- A user changing their password, or an admin resetting it, signs out every session of that user too.
- Each revocation is audited (`session.revoke`, `all: true` for every session of a user).

Revoking sessions doesn't stop a user's [API keys](/administration/api-access-policy); revoke those separately, or
disable the user.

## Session lifetime and API key expiry {/* #session-lifetime-and-api-key-expiry */}

**Admin → Session**:

<Screenshot id="admin-session-settings" alt="Admin → Session: sign out after inactivity 60 minutes, and the API key expiry policy (longest lifetime, allow keys that never expire)" />

- **Sign out after inactivity**: minutes without activity after which a session ends (default 60). Clicks, key
  presses and the requests they cause count as activity, in any tab; a screen's own automatic refresh doesn't, so
  a tab left open still ends. A session ends at the latest **12 hours** after sign-in (or after the inactivity
  time, if you set it longer), then the user signs in again. A change applies to every session from its next
  activity on.
- **API key expiry**: the longest lifetime a new or regenerated key may get, and whether keys without an expiry
  are allowed ([API access policy](/administration/api-access-policy#expiry-policy)).

## Two-factor authentication {/* #two-factor-authentication */}

**You want to:** require a code from an authenticator app as well as the password.

**Admin → Session → Two-factor authentication** sets the policy for **local and LDAP** accounts. Azure AD accounts are
not affected: require MFA for them in Entra and under [Azure AD](./azure-ad.mdx#require-mfa).

{/* shoot first (screenshots/scenes.mjs, 2.24 image), then uncomment: <Screenshot id="admin-two-factor-policy" alt="Admin → Session: the Two-factor authentication card with the policy Off, Optional, Required for admins and Required for everyone, and Save" /> */}

| Policy | What happens |
|---|---|
| **Off** (the default) | Nobody is asked for a code, and the account menu doesn't offer it. |
| **Optional** | Users may set it up from the account menu ([Two-factor authentication](../user-guide/two-factor.mdx)); those who did are asked for a code. |
| **Required for admins** | Admins without it set it up on their next sign-in; others may. |
| **Required for everyone** | Every local and LDAP user without it sets it up on their next sign-in. |

- Choosing a required policy asks first and says how many accounts don't have it yet (*N accounts don't have it yet:
  they will have to set it up on their next sign-in.*).
- **A change applies from each user's next sign-in.** Open sessions go on.
- Someone the policy requires it of and who hasn't set it up signs in to a session that can only set it up: the
  blocking **Set up two-factor authentication** dialog, with **Sign out** as the only other way out. Every other API
  call answers `403` `two_factor_enrollment_required`. A password your admin set is changed first.
- **Turning it off keeps what users set up.** Nobody is asked for a code while it is off; back on, everyone who had
  it set up uses it again, without setting it up again.
- [API keys](/administration/api-access-policy) are not affected by the policy.
- Users who lost their phone and recovery codes: [Reset 2FA](/administration/users#edit-reset-disable-delete). A
  locked-out admin with no other admin: `TWO_FACTOR_RESET_USER`
  ([Troubleshooting](/operations/troubleshooting#sign-in-fails)).

Saving is audited as `settings.update` (the summary has `two_factor_policy`); setting up, sign-in codes, new recovery
codes, turning off and resets as `two_factor.*` ([Audit events](/reference/audit-events)). Codes, keys and recovery
codes are never written to the audit log or the server log.
